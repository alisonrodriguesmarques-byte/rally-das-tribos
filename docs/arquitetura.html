Resumo

O sistema é um monólito simples: Node.js + Express serve a API REST e também os arquivos do frontend (HTML, CSS e JavaScript puros, mobile-first). O banco começa em SQLite e o acesso passa por Knex.js, que gera o SQL tanto para SQLite quanto para PostgreSQL — trocar de banco vira uma mudança de configuração, não uma reescrita.

Três decisões sustentam o modelo de dados:

  1. Tudo pertence a um rally. Tribos, participantes, missões, provas e pontos são ligados ao rally_id. Um rally novo começa limpo e os anteriores ficam intactos.
  2. Pessoa é separada de inscrição. Cada jovem/líder existe uma vez em pessoas; o vínculo com a tribo daquele rally fica em membros_tribo (participante) e rally_tribos (cabeça e auxiliar). Assim os líderes se repetem entre rallies sem duplicar cadastro.
  3. Um único livro-razão de pontos. Missões, dinâmicas, provas e lançamentos manuais geram linhas em lancamentos. O ranking é sempre a soma dessa tabela — nunca um total salvo à parte — e cada correção fica em lancamentos_historico.

Escolhas técnicas e motivo
Acesso ao banco
Knex.js (query builder + migrations). Mesmo código para SQLite e PostgreSQL; sem a complexidade de um ORM completo.
Autenticação
Senha com bcrypt; sessão via token JWT em cookie httpOnly (não fica acessível ao JavaScript da página).
Validação
Biblioteca de schemas (ex.: zod) em cada rota de escrita, para nunca gravar pontos inválidos.
Gráficos
Chart.js servido localmente.
Ranking
Calculado por consulta (view vw_ranking). Com 12 tribos e alguns milhares de lançamentos a soma é instantânea, e não existe total desatualizado.
Testes
Jest + Supertest na API, com banco SQLite em memória.

Como as entidades se relacionam

  • rallies 1—N rally_tribos N—1 tribos. Ao criar um rally, o sistema cria automaticamente as 12 rally_tribos, copiando cabeça e auxiliar do rally anterior.
  • pessoas 1—N membros_tribo N—1 rally_tribos. Um jovem participa de uma tribo por rally (uma inscrição ativa por vez); transferências ficam como linhas encerradas.
  • pessoas 1—1 usuarios (opcional). Só quem faz login precisa de usuário. O papel na tribo (cabeça, auxiliar, participante) vem do rally ativo, então mudar o cabeça de uma tribo já muda a permissão.
  • missoes 1—N missao_entregas. Cada tribo envia sua entrega; ao ser aprovada vira 1 lançamento.
  • provas 1—N questoes 1—N alternativas / respostas_aceitas. provas 1—N tentativas 1—N respostas. O resultado por tribo (prova_resultados) vira 1 lançamento.
  • lancamentos 1—N lancamentos_historico. Toda criação, edição ou cancelamento registra valor anterior, novo valor, motivo, usuário e horário.
  • lancamentos N—1 categorias → pontos por categoria. data_referencia − início do rally → número da semana → evolução semanal.

Decisões em aberto

Quem responde as provas?

O exemplo "Judá — 850 pontos" sugere uma resposta por tribo. O modelo suporta os dois modos (modo = tribo ou individual, somando/média dos jovens). Qual será o padrão?

Pontos individuais.

Os pontos vão só para a tribo, ou também quer um ranking de jovens? (O campo lancamentos.pessoa_id já permite isso.)

Entregas de missão.

Os cabeças vão enviar os resultados pelo sistema, ou no início você mesmo lança tudo a partir do WhatsApp?

Hospedagem.

SQLite precisa de um servidor com disco persistente (ex.: VPS, Railway, Render com disco). Vale definir antes do deploy.
